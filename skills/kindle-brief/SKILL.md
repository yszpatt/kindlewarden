# 向副屏发布简报

副屏是常驻的、只读的、**一屏且不能滚动**的电子墨水屏。
它只承载**结论**，不承载**过程**。

> 核心原则：**一个任务一次。副屏被刷屏后就失去了价值。**

---

## 0. 可用工具与异步语义

| 工具 | 用途 |
|---|---|
| `warden_publish_brief` | 发布一条简报（**主要工具**） |
| `warden_list_recent` | 看副屏上现在有什么 —— **发布前先调它去重** |
| `warden_pin` | 钉住一条，永不过期 |
| `warden_retract` | 撤下一条 |
| `warden_add_todo` | 往待办板加一条（给**人**看的） |
| `warden_alert` / `warden_clear_alert` | 挂起/清除「需要你介入」告警 |
| `warden_status` | 查发件箱积压与投递状况 |

### ⚠️ 发布是**异步**的

`warden_publish_brief` 只是把内容写进本地发件箱就立刻返回，
后台线程再异步投递到副屏服务。

这意味着：

- **返回 `queued: true` 不等于已经上屏** —— 副屏可能几十秒后才刷新
- 副屏服务没开、网络断了、Kindle 关机，**都不影响调用成功**，内容会排队等着
- 所以**不要**为了「确认送达」而反复重发
- 真的怀疑没送到，用 `warden_status` 查积压条数，而不是重发

### ⚠️ 告警有生命周期

`warden_alert` 会一直挂在副屏顶端，直到你调 `warden_clear_alert`。
**问题解决了就要清掉**，否则真正的告警会被一条过期的挡在后面。

## 1. 何时发布

### ✅ 应该发布
- 完成一个用户交给的**多步骤任务**
- 修复了一个 bug **并验证通过**
- 完成一次部署 / 发布 / 迁移
- 得出一个需要用户知道的**结论或发现**
- 任务失败、或需要用户介入才能继续

### ❌ 不要发布
- 单个文件的编辑、单次命令执行
- **任何中间步骤** —— 用户不需要知道「第 3 步做了什么」
- 纯信息查询（读文件、搜索、浏览）
- 同一任务的连续小改动 → **合并成一次**，或用 `supersedes` 更新
- 你只是「开始了」某件事（副屏不是进度条）

### 判定方法
问自己：**这条信息，用户一小时后回头看还有价值吗？**
如果只是「此刻正在发生」，不要发。主屏（终端）已经显示了。

---

## 2. 怎么写 title

标题是**结论**，不是**过程**。

| ✗ 错误 | ✓ 正确 |
|---|---|
| 执行了 12 次工具调用并修改了 3 个文件 | 修复了 auth 模块 token 刷新的竞态条件 |
| 开始处理数据库迁移 | 数据库迁移到 PostgreSQL 16，停机 40 秒 |
| 完成了任务 | 重构了订单服务，测试覆盖率 68% → 91% |
| 分析了一些性能问题 | 定位到 N+1 查询，列表接口 P95 从 2.1s 降到 240ms |

**规则：**
- **≤ 20 个中文字**，一句话。副屏上标题区宽 854px，44px 字号下纯中文约 19 字就满了，
  超出会被截断成 `…`（夹杂英文标识符可适当放宽）
- 包含**结果**，不是动作
- 尽量带**可量化的变化**（数字最有说服力）
- 中文优先（副屏主人是中文用户），但代码标识符保持原文

## 3. status 怎么选

| 值 | 含义 | 判定标准 |
|---|---|---|
| `ok` | 完全达成 | 目标全部完成且已验证 |
| `partial` | 部分达成 / 有遗留 | 主要目标达成，但有已知未完成项（**必须在 summary 里说明**） |
| `failed` | 未达成，需要介入 | 无法继续，或验证不通过 |
| `info` | 无需行动的结论 | 观察、调研结果、方向性建议 |

`failed` 和 `partial` 的简报会在副屏上保留更久（因为需要人处理），
所以**不要滥用** —— 用 `ok` 汇报正常完成的事。

---

## 4. 怎么写 summary

### 两个显示位置，两条不同的长度规则

| 位置 | 怎么显示 | 长度要求 |
|---|---|---|
| **看板**（默认视图） | **单行截断** | **≤ 28 个中文字**，超出会被 `…` 切掉 |
| **详情页**（点卡片进去） | **全文折行 + 分页** | 没有硬上限，但要遵守下面的格式要求 |

所以：

- 看板上那 28 字是**第一句的门面**，必须独立成句、说清结论 ——
  截在句子中间会显得很草率
- 详情页可以展开，**但展开不等于啰嗦** —— 见下面的格式要求

### ⚠️ 格式要求（详情页是要读的）

详情页会**保留你的换行**，并自动：
- 按段落排版，段间留白
- 以 `-` / `*` / `1.` 开头的行渲染成**列表项**（带统一的项目符号）

所以**主动分段**，不要写成一大坨。推荐的结构：

```
先给结论（一句话，这句也会成为看板上的那 28 字）。

如果有多个原因/步骤：
- 原因一：一句话说清
- 原因二：一句话说清

最后说影响或后续（需要用户做什么）。
```

### 写摘要的要求

**条理清晰**：一个意思一段，不要把三件事挤在一句里。
**表述精确**：说"输入抑制状态没恢复"而不是"有点问题"；说"每 60 秒重绘一次"而不是"经常重绘"。
**不繁琐**：能一句说清就别写三句。删掉"我首先…然后…接着…"这类过程叙述。
**容易理解**：用具体名词和动词，不用抽象黑话。读者可能是几小时后回看的你自己。

### 回答三个问题（能答几个答几个，优先第 3 个）

1. **做了什么**
2. **结果如何**
3. **需要用户注意什么**（最重要，也最常被漏掉）

### 不要复述步骤

不要写「我先…然后…最后…」。不要重复 title 已经说过的话。

```
✓ 查出两个独立原因。

   一是旧 shell 客户端用 fbink 直接刷屏，覆盖了插件画的退出按钮。
   二是 KOReader 的输入抑制状态在待机异常时没有恢复。

   已修：启动时清理竞争者、每轮轮询自愈输入。

✗ 先看了日志，发现有报错，然后我去查了 crash.log，
   接着发现是 WardenScreen 没有定义，最后我把它改好了，测试通过了。
```

### 反面例子（要避免的写法）

| ✗ 不好 | 问题 | ✓ 改法 |
|---|---|---|
| 解决了若干问题 | 没说是什么问题 | 修掉了退出按钮消失和触摸失效 |
| 经过深入分析定位到根因 | 过程叙述，零信息 | 根因是旧客户端在抢屏 |
| 优化了性能，效果显著 | 没有数字 | 列表接口 P95 从 2.1s 降到 240ms |
| 修改了 a.lua、b.py、c.sh | 不该列编辑过的文件 | 用 artifacts 给用户会打开的东西 |
| 这个问题比较复杂，涉及多个方面 | 全是空话 | 两个原因：抢屏、输入抑制未恢复 |

## 5. artifacts

只列**用户真的会去打开**的东西：

- ✅ PR / commit 链接
- ✅ 生成的文件路径（报告、图表、导出物）
- ✅ 部署地址 / 预览链接
- ✅ 相关 issue

- ❌ 中间产物、临时文件
- ❌ 你编辑过的源文件列表（除非用户要的就是这个）
- ❌ 日志文件（除非用户明确要）

最多 5 条。

---

## 6. 必须避免的内容

副屏是**常亮摆在桌面上的**，相当于半公开显示。以下内容**绝对不要**出现在简报里：

- ❌ 任何密钥、token、密码、连接串、私钥
- ❌ 客户数据、个人信息、真实姓名邮箱
- ❌ 大段代码（副屏只有几行字的容量）
- ❌ 内部主机名 / 用户名 / 私有路径前缀（能省则省）
- ❌ 未公开的业务信息

服务端会做正则兜底扫描（`sk-`、`ghp_`、`AKIA` 等模式）并拒绝可疑内容，
但**不要依赖它** —— 被拒绝的简报等于没汇报。

---

## 7. 去重与更新

**发布前先调 `warden_list_recent`**，检查：

1. 同一任务是否已经汇报过？
   → 是：用 `supersedes: "<brief_id>"` 取代那一条，而不是再发一条
2. 副屏上现在有什么？
   → 避免和已有内容重复或矛盾

**同一个任务的多次小改动必须合并。** 副屏不是日志。

---

## 8. 频率上限

- 一个任务 **最多一条**简报
- 短时间内的多条相关简报 → 合并
- 如果一次会话里你发现自己在发第 4 条以上简报，**停下来重新审视**：
  你是不是在把过程当结论发？

---

## 9. 参考调用

```json
{
  "title": "修复了 auth 模块 token 刷新的竞态条件",
  "status": "ok",
  "summary": "定时器刷新改为惰性刷新，补 4 个并发测试",
  "project": "backend",
  "artifacts": ["https://github.com/org/repo/pull/482"],
  "duration_s": 1860
}
```

对应 MCP 调用：

```
warden_publish_brief(
  title="修复了 auth 模块 token 刷新的竞态条件",
  status="ok",
  summary="定时器刷新改为惰性刷新，补 4 个并发测试",
  project="backend",
  artifacts=["https://github.com/org/repo/pull/482"],
  duration_s=1860,
)
```

更新先前那条（而不是再发一条）：

```
warden_publish_brief(
  title="修复了 auth 竞态条件（已补回归测试）",
  status="ok",
  supersedes="brief_9f2a1c3d4e",
)
```

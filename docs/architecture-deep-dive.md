# kindlewarden — 架构深水区（第二轮）

> 前提：已确定采用**越狱 + FBInk 直绘**路径（放弃浏览器方案）。
> 本文只讨论架构判断，不含实现。文末有三个需要你定的参数。

---

## 1. 架构基石：复杂度放在哪一边

**原则：把复杂度放在你能 ssh 进去调试的机器上，而不是放在 Kindle 上。**

### 1.1 一个需要修正的说法

我上一轮说「FBInk 不能显示中文，所以必须服务端渲染」——这话说重了。核实 FBInk README 后的准确情况：

| 事实 | 来源 |
|---|---|
| FBInk 默认用**内置固定点阵字型**，不含 CJK | README |
| `UNIFONT=1` 可嵌入 GNU Unifont，但官方明确警告：*"the font is actually split in two (double-wide glyphs are punted off to a specific font), which may dampen its usefulness in practice"*，且增加约 2MB | README |
| FBInk **支持 TrueType/OpenType 渲染**（`OPENTYPE=1`） | README |
| FBInk 图像支持 JPEG/PNG/TGA/BMP/GIF/PNM，以及 raw Gray8/RGB32（±Alpha） | README |
| 支持按矩形区域绘制（`-g` 的 `top/left/w/h`，参数名以 `fbink --help` 为准） | CLI.md |
| 波形可选（`gc16`/`gl16`/`a2` 等），决定刷新质量与闪烁 | CLI.md |
| 有 Go 绑定 [go-fbink-v2](https://github.com/shermp/go-fbink-v2)、Python `py-fbink`、Rust、LuaJIT | README |
| 有 `INPUT=1` 编译项与 `fbink_input_scan` 工具（处理 evdev 输入） | README |
| 编译期可裁剪（`MINIMAL` + `DRAW`/`BITMAP`/`IMAGE`/`FONTS`/`OPENTYPE`） | README |

**所以中文在技术上是可以端上渲染的**（OTF 路径 + 放一个 CJK 字体文件到设备上）。

### 1.2 但结论仍然是服务端渲染

不是中文的问题，是**布局引擎的归属**问题：

端上渲染 = 你需要在 C 或 Go 里自己实现换行、对齐、卡片布局、进度条、图标、灰阶抖动。
这些逻辑会住在整个系统里**最难调试、最难迭代、最容易变砖**的那台设备上。

服务端渲染 = 布局复杂度留在 host（Python/Node，随手改随手看），Kindle 端退化成一个
40 行的「下载 PNG → blit」循环。

**代价对比：**

| | 服务端渲染 PNG | 端上 FBInk 绘制 |
|---|---|---|
| 单次传输 | 1-bit 全屏 PNG ≈ 10–40KB | 几百字节 JSON |
| Kindle 端 CPU | PNG 解码（PW3 上 <100ms 量级，可忽略） | 文本排版（弱 CPU 上是实打实的负担） |
| 布局迭代 | 改代码即生效 | 交叉编译 + 推送 + 重启 |
| 中文 | 天然支持 | 需装字体，仍需自己排版 |
| Kindle 端代码量 | ~40 行 | 一个应用 |

LAN 上 40KB 不是问题。**选服务端渲染。**

> 例外：若你的最终画面是「极简纯英文状态」，端上渲染能省一个组件。但省下的复杂度远小于失去的迭代速度。

## 2. 更新粒度：全局刷新 vs 脏区域

e-ink 的体验瓶颈**不是延迟，是闪烁**。

- 全屏刷新：整屏闪黑 200ms–1s，很打断
- 局部刷新：只重绘变化矩形，200ms 内几乎无感

### 2.1 协议设计

把画面切成**逻辑块**（不是等分条带，而是「卡片」为单位，每块有稳定 id 和 bbox）：

```
GET /rev
→ {
    "global_rev": "a3f9c1",
    "generated_at": 1791609294,
    "source_health": "ok",
    "blocks": [
      {"id": "banner",  "bbox": [0,0,1072,220],   "hash": "9f2a"},
      {"id": "task-1",  "bbox": [0,220,1072,300], "hash": "c71e"},
      {"id": "footer",  "bbox": [0,1300,1072,148],"hash": "0d43"}
    ]
  }
```

客户端只拉取 hash 变化的块（`GET /block/<id>.png`），局部 blit。

### 2.2 两个必须遵守的约束

1. **块边界必须对齐内容边界**，否则文字跨越块边界会被撕裂。
   这是**信息架构约束**，不是实现细节 —— 布局设计时就要按「卡片」切。
2. **残影**：局部刷新会累积残影。每 N 次局部刷新后强制一次全刷（选 `gc16` 波形）。

### 2.3 但先问：值得吗？

对一个**更新频率低**的告警看板，脏区域更新的收益接近于零。

只有当画面上存在**持续变化的元素**时才明显划算：
- 秒级心跳（"12 秒前更新"）
- 倒计时 / ETA
- 实时百分比进度条
- 日志尾巴滚动

**→ 这是需要你决定的参数之一（见 §10）。**

**架构建议：P4 先做全屏全局刷新，但从现在起协议里就带上 `bbox` 和 `blocks` 字段。**
这样以后升级到局部刷新**不需要改协议**。零成本的架构预留。

## 3. 实时性模型：Kindle 无法被唤醒

**硬约束：host 无法主动推送到 Kindle。** 实时性上限完全由客户端决定。

| 方案 | 延迟 | 功耗 | 复杂度 |
|---|---|---|---|
| 短轮询（5s） | 平均 2.5s | 每次 wget 重新建连，可能反复唤醒 WiFi | 低 |
| **长轮询（hold 55s）** | **接近 0** | WiFi 保持关联，CPU 阻塞在 recv | 中 |
| SSE / WebSocket | 接近 0 | 同长轮询 | 高（老设备上不值得） |

### 推荐：长轮询

```
GET /wait?rev=a3f9c1&timeout=55
  → 200 + 新 rev    （有变化，立即）
  → 204             （超时，无变化）
```

### 反直觉但重要的点

**轮询更频繁 ≠ 更实时，反而更耗电。**
长轮询是「低功耗 + 低延迟」能同时成立的少数方案。

### 客户端形态

`wget` 做长轮询的超时控制很笨拙。建议 Kindle 端是**静态编译的 Go 二进制**：
- 有现成绑定 [go-fbink-v2](https://github.com/shermp/go-fbink-v2)
- 可测试、可日志、可自更新、可处理信号
- 长轮询 + blit + 退避重连都在一个进程里

这比 shell 脚本健壮一个量级，而越狱社区跑静态 Go 二进制是常规操作。

## 4. 状态推断层（最容易被低估的部分）

事件流是**低层**的（`step/*`、`tool/*`、`llm/retry`），
看板要的是**高层**的（"在重构 auth 模块，卡在跑测试"）。

这两者之间需要一个**推断器**，它不是 switch-case 映射。

### (a) 任务单元的粒度

候选：`session` / `turn` / `todo` 条目 / `subagent`。

**建议：以 `todo/write` 的条目作为主骨架** —— 它是事件流里最稳定的高层语义信号
（agent 自己写的计划清单，天然就是给人类看的粒度）。
`turn` 作为生命周期边界，`tool/call` 提供「此刻在做什么」的一手描述。

### (b) 命名优先级

```
session/title  →  会话名
todo/write     →  步骤名
tool/call      →  当前动作
─────────────────────────────
拼装 → "重构 auth 模块 · 正在编辑 src/auth.ts"
```

### (c) 时间维度 —— stalled 检测 ⭐

**这是 e-ink 看板最有价值的功能：告诉你「它卡住了」。**

- 规则：`step/start` 之后超过 T 秒没有 `step/end` → 疑似卡住
- **T 不能是常数**：LLM 思考本来就要 30–60s，定死会一直误报
- 建议 `T = max(90s, 该会话历史步长中位数 × 3)`，自适应
- `llm/retry` 连发 → 判定「正在重试」。这是**好**信号（说明还活着），不要和卡住混淆
- 无事件 ≠ 卡住（可能只是长时间工具调用）→ 需要区分「安静」和「异常安静」

### (d) 嵌套折叠

subagent 树可能很深。屏幕上只放 2 层：主任务 + "3 个子任务运行中"。
更深层只在 focus 模式下展开。

### (e) 架构建议：推断器是纯函数

```
events[] → ViewModel          （纯函数，无 IO，无时间依赖注入外）
ViewModel → pixels            （纯函数）
```

好处：**可回放、可快照测试、可 diff。**
"看板显示错了" 从一个玄学问题变成一个可复现的 bug。
在调试阶段这个价值非常大 —— 你可以把一段真实事件流冻结成测试固件。

## 5. 看板的「诚实性」

**e-ink 看板最大的失败模式是说谎**：画面看起来很确定，其实是 3 小时前的。
（对比 LCD 仪表盘：它至少还在闪，看得出来活着。）

三种失败必须可区分：

| 情况 | 看板应显示 |
|---|---|
| DSH 会话正常结束 | "会话已结束"（正常终态） |
| collector 挂了 | "数据陈旧 X 分钟"（Kindle 无法知道 collector 死活，只能靠帧内时间戳） |
| 网络断了 | "连接中断 X 分钟"（Kindle 本地计时） |

**设计规则：**
1. 每一帧内嵌 `generated_at` + `source_health`
2. Kindle 端用**本地时钟**算 age，不信任远端时间
3. **宁可显示「我不确定」，也不要显示可能过期的确定信息**

**对协议的影响：** 光有 `/screen.png` 不够。`/rev` 响应必须带 `generated_at` 和 `source_health`
（§2.1 的响应体里已经包含）。

## 6. 存储：事件溯源，而不是状态表

collector **不要**写「当前状态」表。写 append-only 的领域事件 log。

理由：
- 与 DSH 自身的设计哲学一致（它的会话日志就是事件流）
- **可回放**：改了布局后能重现历史画面
- **崩溃恢复** = 从 log 重建，不需要额外机制
- 调试与审计天然具备
- 成本：就是个 JSONL 文件，零依赖

renderer 是 log 的**投影**。

于是整个系统是一条干净的管道：

```
外部事件流 → 归一化 → 领域事件 log → 推断 → ViewModel → 投影 → PNG → 传输 → blit
                ↑                      ↑                   ↑
            可重放                纯函数              纯函数
```

**每一层都可以单独测试，每一层都可以替换。**

## 7. 越狱解锁的新可能：Kindle 是触摸屏

PW3 有触摸屏。FBInk 提供 `INPUT=1` 编译项和 `fbink_input_scan`（README 里用于识别 evdev 设备），
说明读输入在 FBInk 生态里是支持的。

**理论上**看板可以双向：点某行 → 确认告警 / 切换焦点 / 取消任务。

### 但要冷静

- e-ink 触摸反馈慢：点击后要等局部刷新才看到「按下」态
- 需要一整套 UI 状态机（选中态、确认态、超时回退）
- **安全边界问题**：从桌上一块屏点一下就能取消 agent 正在跑的任务？风险不低
- 需要命中测试 + `action_id` 白名单

### 建议

**先做只读看板。** 把输入当作 P5 可选分支，但现在就在协议里预留：
`/meta` 或 `blocks[]` 里带 `hitbox` 和 `action_id`。

**真正低成本的回传其实是「单按钮语义」**：长按屏幕 = 确认当前告警 / 切到下一个会话。
不需要命中测试，不需要 UI 状态机，却覆盖了 80% 的回传价值。

## 8. 多会话焦点编排

本机实测存在多个工作区会话（至少 4 个）。必须回答：**谁上屏？**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部聚合总览 | 信息全 | 容易乱，屏幕上放不下 |
| B. 单一「焦点会话」 | 清晰、字大 | 需要选择算法 |
| C. 总览 + 触摸切换 | 兼顾 | 需要输入（见 §7） |

**焦点算法建议：**
```
优先级 = 需介入 > 失败 > 最近活跃 > 其它
```
并且 **焦点必须稳定** —— 不要每 5 秒跳来跳去，那比不显示还糟。
提供显式 pin（MCP 工具或配置文件）。

## 9. 网络可达性与设备注册

- Kindle 老浏览器不支持 mDNS；越狱路径的 Go 客户端可以自己实现，但没必要
- host IP 可能因 DHCP 变化，两个方案：
  - **(a) DHCP 保留 / 静态 IP** —— 最简单，推荐
  - **(b) Kindle 主动注册**：`POST /register {device_id, ip, battery, rssi}`
    → host 记录，IP 变了自动修正

(b) 顺带解决另一个问题：**`/device/status` 的数据来源**（电量、信号、最后在线时间）。
越狱路径下客户端是自己写的 Go 程序，上报这些都是顺手的事。

**建议：先 (a)，但把 (b) 的接口留出来** —— 成本几乎为零，收益是运维省心。

## 10. 需要你定的三个架构参数

这三个直接决定协议和渲染设计，现在定了后面不用返工：

### 参数 1：实时性要求
- **秒级**（要长轮询 + 脏区域更新）—— 适用于「盯进度」场景
- **分钟级**（短轮询 + 全屏刷新就够）—— 适用于「告警看板」场景

### 参数 2：中文是硬需求吗
- 是 → 服务端渲染是**不可动摇的基石**（§1）
- 否 → 端上渲染仍不是好选择，但至少不必纠结字体

### 参数 3：画面上要有「持续变化」的元素吗
- 有（秒级心跳、倒计时、百分比）→ 脏区域更新值得做
- 无 → P4 直接全刷，协议字段留着备用就行

### （附带）参数 4：焦点策略
全部聚合总览，还是单一焦点会话？

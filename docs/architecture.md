# kindlewarden — 设计 v2（副屏定位）

> **v2 相对 v1 的定位修正：**
> v1 把 Kindle 当成「agent 运行状态监控屏」，主通道是旁路观测 DSH 会话事件流。
> 这个定位有两个实质缺陷：
> 1. **绑死单一 harness** —— DSH 私有 `session.v4.jsonl.zstd` 格式，跨终端即失效
> 2. **粒度错了** —— 事件流是 step 级的，但副屏不需要知道「第 3 步调了什么工具」；
>    用户要的是**结论**，不是**过程**
>
> **v2 定位：Kindle 是副屏（ambient display），承载「沉淀下来的结论」。**
> 主通道是 **MCP 主动发布简报**。事件流观测降级为「仅 DSH 可用的可选增强」。
>
> 本文取代 v1 的对应章节；`design.md` 与 `architecture-deep-dive.md` 中的
> **技术核实结果仍然有效**（FBInk 参数、越狱路径、刷新型号等），
> 但架构结论以本文为准。

## 0. 副屏的信息哲学

主屏与副屏的分工是理解一切的起点：

| | 主屏（终端） | 副屏（Kindle） |
|---|---|---|
| 时间性 | 实时、滚动即逝 | **沉淀、常驻** |
| 粒度 | 细（每一步、每个 token） | **粗（只放结论）** |
| 交互 | 双向、需要操作 | **只读**（PW3 有触摸，但见 §9） |
| 注意力 | 抢占式 | **余光可见即可** |
| 容量 | 无限滚动 | **一屏，且不能滚动** |

**推论：副屏上不该出现任何「过程」。**
「正在执行第 3 步」这类信息属于主屏。副屏只回答三个问题：

1. **发生完了什么？**（简报流 ← 核心板块）
2. **需要我做什么？**（告警）
3. **现在是怎样的？**（环境 / 状态）

**一条关键原则贯穿全图：**

> **agent 提供内容，人类配置结构，服务端决定排版。**

agent 永远不说「放到左上角、字号 40」。它只说「发生了什么」。坐标和字号是服务端的事。

## 2. MCP 接口设计（核心）

### 2.1 传输形态：瘦客户端 + 异步上报

**为什么不是「MCP server 直接暴露在 host 上」？**

因为那会让 agent 的 tool call 依赖网络——副屏 host 重启或网络抖动时，agent 会收到错误、需要重试、甚至中断任务。**副屏永远不该影响主屏的工作。**

**推荐形态：每个终端装一个 stdio 瘦客户端。**

```
agent ──stdio──▶ warden-mcp（瘦客户端）
                    │ ① 立即写本地持久队列，返回 {accepted: true}
                    │ ② 后台线程异步 POST 到 host
                    │ ③ 失败则退避重试（本地队列不丢）
                    ▼
                 副屏 Host
```

好处：
- ✅ agent 的 tool call **永远是亚毫秒级的本地写**，不可能被网络拖慢
- ✅ host 挂了、Kindle 关机、网络断了，agent 完全无感
- ✅ stdio 是 MCP 最成熟的形态，各 harness 都支持
- ✅ 瘦客户端是单文件脚本，部署成本极低

代价：每个终端要装一次。（后续可加 HTTP transport 供「远程终端懒得装」的场景，但**不是默认**。）

### 2.2 工具集

**面向简报：**

```
warden_publish_brief(
    title:       str,          # 必填。一句话结论，≤20 个中文字
    status:      str,          # 必填。ok | partial | failed | info
    summary:     str  = "",    # 可选。1–3 句
    artifacts:   list = [],    # 可选。最多 5 条 {label, kind, ref}
    project:     str  = "",    # 可选。项目名，用于分组
    tags:        list = [],    # 可选
    duration_s:  int  = 0,     # 可选
    supersedes:  str  = "",    # 可选。取代此前的某条简报（防刷屏）
) -> {brief_id, rev, accepted: true}
```

**辅助：**

```
warden_list_recent(limit=10)      # 读副屏当前内容 → 用于去重、避免重复汇报
warden_pin(brief_id, pinned=true) # 钉住，不被老化挤掉
warden_retract(brief_id)          # 撤销（一般用 supersedes 代替）
warden_note(text, ttl_h?)         # 极简一行便签
warden_status()                   # 副屏健康状况（host 是否可达、板上有几条）
```

**MCP Resources：**

```
warden://board/current   →  当前副板上所有内容的文本表示
warden://board/health    →  {host_reachable, queued, last_sync, board_rev}
```

### 2.3 三个接口设计决策

**(a) 字段尽量可选、尽量不报错。**
必填只有 `title` 和 `status`。其他全有默认值。
字段超长自动截断而不是报错。**宁可展示一份不完美的简报，也不要让 agent 卡在格式校验上。**

**(b) `warden_list_recent` 不是可有可无的。**
多终端共用一块屏 → agent 需要能「看见别人发了什么」和「我是不是已经发过了」。
这是副屏作为**共享资源**的基础能力。

**(c) `supersedes` 解决刷屏。**
同一任务反复小改动 → 用 `supersedes` 替换而非追加。
否则副屏会被同一个任务的十条简报淹没。

## 3. Skill 设计（以及一个关键洞察）

### 3.1 关键洞察：tool description 是唯一跨 harness 的注入点

不同 harness 的 skill 机制完全不同（Claude Code 有 skills、Codex 有 AGENTS.md、
Cursor 有 rules、有些什么都没有）。

**但所有 harness 都读 MCP 工具的 description。**

所以：
- **简报风格的核心要求必须写进 `warden_publish_brief` 的 description**
- Skill 是**增强版**（更详细的规则 + 触发时机 + 示例）
- 这样即使 harness 不支持 skill，行为也大致正确

### 3.2 工具 description 里必须塞进去的最小约束

```
title: 一句话结论，不是过程。≤20 个中文字（超出会被截断）。
  ✗ "执行了 12 次工具调用并修改了 3 个文件"
  ✓ "修复了 auth 模块 token 刷新的竞态条件"
summary: 1–3 句。做了什么、结果如何、需要人注意什么。不复述步骤。
status: ok=完全达成 / partial=部分达成或有遗留 / failed=未达成需介入 / info=无需行动的结论
不要包含密钥、token、客户数据、大段代码。
同一任务只发一次；更新用 supersedes。
```

### 3.3 Skill 全文草稿

见独立文件 [`skills/kindle-brief/SKILL.md`](../skills/kindle-brief/SKILL.md)。

核心竞争力在「何时发 / 何时不发」的判定上——**这是简报流质量的决定因素**。
一个什么都汇报的 agent 会让副屏变成噪声源，比空白更糟。

## 4. 板块系统（副屏的功能规划）

### 4.1 板块抽象

```
板块 = 数据源 + 渲染器 + 优先级 + 空间策略
```

| 板块 | 内容 | 优先级 | 空间 |
|---|---|---|---|
| `alerts` | 需要人介入的告警 | **抢占**（仅存在时占位） | 固定 |
| `briefs` | **任务完成简报流（核心）** | 高 | 弹性 |
| `todos` | 待办 / 下一步 | 中 | 弹性 |
| `ambient` | 时间、日期、天气、室内环境 | 低 | 固定小 |
| `health` | host CPU/内存/磁盘、CI 状态 | 低 | 弹性 |
| `notes` | 便签 / 从主屏扔过来的暂存 | 中 | 弹性 |
| `statusbar` | 数据年龄、源健康度、简报计数 | **必有** | 固定 1 行 |

### 4.2 布局策略：垂直堆叠 + 权重（不是自由坐标）

**明确否决自由坐标布局**（先例项目 `kindle-mcp-dashboard` 用的是归一化 1000×1000 画布 +
任意区域定位）。理由：

- 自由坐标要求配置者理解像素/比例，容易做出难看的排版
- 内容变长时自由坐标布局会**溢出并破坏**整个画面
- 垂直堆叠天然处理内容伸缩：板块内部截断，而不是溢出

**空间分配规则：**

```
┌──────────────────────────────┐
│ alerts        （存在才占位）   │  固定
├──────────────────────────────┤
│                              │
│  briefs  ┐                   │  弹性，按 weight 分配
│  todos   ├─ 剩余空间          │  剩余高度
│  notes   ┘                   │
│                              │
├──────────────────────────────┤
│ ambient + health             │  固定小
├──────────────────────────────┤
│ statusbar                    │  固定 1 行
└──────────────────────────────┘
```

**关键：`briefs` 显示几条，是由渲染器算出来的，不是配置的。**
可用高度 ÷ 每条简报的高度 = N 条。这是 §0「服务端决定排版」的具体体现。

### 4.3 其他功能板块的定位建议

用户问「作为副屏如何规划其他功能」。按价值排序：

**高价值（建议先做）**
- `alerts` —— 副屏最有价值的瞬间是「需要你介入」。常亮、余光可见、比手机推送更不打扰
- `todos` —— 「下一步做什么」，跨终端共享的待办
- `ambient` —— 时间/日期/天气。低成本、高日常价值，让副屏即使在没任务时也有用

**中价值**
- `health` —— host 负载、CI/构建状态。适合「我有台机器在跑东西」的场景
- `notes` —— 从主屏扔过来的剪贴板/便签

**低价值 / 谨慎**
- 番茄钟、倒计时等**动态元素** —— 你在参数 3 已排除（会迫使刷新频率上升，代价大）
- 日历日程 —— 信息量大但 e-ink 上一屏放不下，且需要额外集成
- 自由 dashboard widget —— 参见 §4.2 的否决理由

## 5. 多终端竞争与简报生命周期

这是 v1 没有的问题：**一块屏，多个终端写**。

### 5.1 板上策略（配置项）

| 策略 | 行为 | 适用 |
|---|---|---|
| `all` | 全部按时间倒序混排 | 默认，单人多终端 |
| `project` | 按 project 分组 | 多项目并行 |
| `focus` | 只看指定 project / machine | 专注模式 |

### 5.2 老化与保留

副屏是「沉淀」的，但不能无限堆积。

| 规则 | 值（可配） |
|---|---|
| 简报可见窗口 | 最近 24h |
| `failed` 简报保留 | 更久（72h）—— 因为需要人处理 |
| 被 `pin` 的简报 | **永不过期** |
| 屏幕容量 | 由渲染器算（§4.2） |

### 5.3 e-ink 不能滚动 → 这是硬约束

PW3 有触摸屏，但**不做滚动交互**（理由见 §9）。所以：
- 只显示最近 N 条，老的自动消失
- 重要的靠 `pin`
- 没有「翻页看历史」这个能力 —— **设计时要接受这个限制，而不是绕过它**

## 6. 保持不变的技术部分

以下从 v1 继承，**未被本次定位调整影响**：

### 6.1 渲染规格

| 项 | 值 |
|---|---|
| 尺寸 | 1072×1448（PW3 原生） |
| 色彩 | **8-bit 灰度 PNG（`L` 模式）** |
| 格式 | PNG（**实测**：服务端直接输出 97KB；预量化到 16 灰阶后 65KB） |

**不要用 1-bit** —— 中文小字号在无抗锯齿下会糊成一团。设备有 16 灰阶。

### 6.2 FBInk 命令与两处已知坑

```sh
fbink -g file=/tmp/warden.png,dither -W GC16 -f -q
```

| 参数 | 作用 |
|---|---|
| `dither` | **软件** ordered 8×8 抖动，匹配 16 灰阶调色板 |
| `-W GC16` | 16 级灰阶全质量波形 |
| `-f` | 闪刷，清残影 |
| `-q` | 安静模式 |

⚠️ **坑 1：PW3 不支持硬件抖动。**
FBInk README 明确：真正的硬件抖动（`-D`）*"completely untested on Kindle"*，
且只有 **Oasis 2 / PW4 / Oasis 3** *可能*支持。PW3 不在列表 → 必须用软件抖动。

⚠️ **坑 2：`-g` 的参数名不是 `top/left/w/h`。**
正确签名：`-g file=PATH,x=NUM,y=NUM,halign=,valign=,w=NUM,h=NUM,dither`
（`top/left/width/height` 是 `--refresh` 的参数）

### 6.3 刷新与轮询

- **短轮询**（分钟级足够，不需要长轮询/SSE）
- `GET /rev` 返回 `next_poll_after` —— **服务端告诉客户端下次何时来**
  - 空闲 → 300s；有新简报 → 30s
- **心跳刷新**：状态静止超 N 分钟（建议 10–15）强制刷一次，只更新时间戳
  - 因为「不变就不刷」会让看板无法自证「还活着」

### 6.4 看板的诚实性（三态）

| 情况 | 显示 |
|---|---|
| 正常 | 数据 N 分钟前 |
| host 不可达 | 数据陈旧 N 分钟 |
| 网络断 | 连接中断 N 分钟（Kindle 本地计时） |

**宁可显示「我不确定」，也不要显示可能过期的确定信息。**

### 6.5 协议契约

```
GET /rev
→ {
    "global_rev": "a3f9c1d2",
    "generated_at": 1791609294,
    "source_health": "ok",          // ok | stale | disconnected
    "next_poll_after": 120,
    "blocks": [...]                 // 预留，当前不用
  }

GET /screen.png      → image/png, 1072×1448 Gray8, ETag=<global_rev>, no-store

POST /brief          → 受件（供瘦客户端异步上报）
POST /pin
POST /retract        → 从副屏拿下，**归档保留**（include_hidden 还看得到）
POST /brief/delete   → **彻底删除**，连归档也不再有
GET  /board          → JSON，供 warden_list_recent 与调试
GET  /board?include_hidden=1 → 连已撤回 / 已被取代的简报一起返回
```

**「撤回」与「彻底删除」是两件事，不要合并**：

| | 事件 | 副屏 | 归档（`include_hidden`） | 用途 |
|---|---|---|---|---|
| 撤回 | `brief.retracted` | 消失 | **还在** | "这条不该在板上" |
| 删除 | `brief.deleted` | 消失 | **不在** | "我压根不想留这条" |

两者都**只追加事件**，日志本身永远不被改写 —— 这是事件溯源的前提。
``clear_all``（「清空看板」）故意走**撤回**而不是删除：
清空是一次可追溯的操作，不是抹掉历史。

### 6.6 设备与越狱

- PW3 / DP75SDI，1072×1448，16 灰阶
- 固件 5.16.2.1.1 = **7~9 代末版固件**，越狱后无 OTA 风险
- [LanguageBreak](https://github.com/notmarek/LanguageBreak) 支持 5.14.3–5.16.2.1.1
- 部署链：LanguageBreak → Hotfix → MRPI → KUAL → FBInk
- 客户端用 **shell 脚本**（分钟级轮询下 Go 二进制无必要）

## 7. 事件流观测的新定位（可选增强）

v1 的 DSH 事件流观测**不再是主通道**，但也没白发现。它现在的定位是：

> **仅当 harness 是 DSH 时，用于「进行中」的轻量补充。**

- 用途举例：状态栏显示「2 个任务进行中」，或在简报流顶部放一行活动指示
- 价值：副屏在没新简报时不会显得「死」了
- **不阻塞设计**：这不是必需品，缺失时系统完全正常工作
- 同样地，它能避免 v1 的「绑死私有格式」缺陷 —— 它是可插拔的增强，不是地基

**这也顺带解决了跨终端问题**：其他 harness 没有这种日志，但不影响它们用 MCP 发简报。

## 8. 分阶段计划（修订）

| 阶段 | 内容 | 依赖设备 | 验收标准 |
|---|---|---|---|
| **P0** | 简报模型 + 渲染器 + `panels.yaml` 布局引擎 | 否 | 喂入假简报，生成正确的 1072×1448 中文看板 |
| **P1** | 受件服务 + 简报存储 + `/rev` `/screen.png` | 否 | curl 发简报 → 浏览器看到更新 |
| **P2** | `warden-mcp` 瘦客户端（stdio + 本地队列 + 重试） | 否 | 任一 harness 里的 agent 能发简报 |
| **P3** | Skill + 工具 description 调优 | 否 | agent 自主发布的简报质量达标 |
| **P4** | 越狱 + Kindle 客户端 + 开机自启 | **是** | 脱离电脑自动运行 24h |
| **P5** | 多终端板上策略 / pin / 老化 | 否 | 两个终端同时写不打架 |
| **P6**（可选） | 事件流进行中指示（仅 DSH） | 否 | —— |

> **P0–P3 全部可以在没碰过 Kindle 的情况下完成。**
> 这是刻意的：最不确定的部分是「简报质量 + 信息设计」，不是设备。
> 先用假数据把版面调到满意，再去碰设备。

## 9. 待定项

1. **板上策略默认值** —— `all` / `project` / `focus`？多终端场景下你实际会怎么用？
2. **哪些板块先做** —— 建议 `alerts` + `briefs` + `statusbar` 起步，`ambient` 紧随
3. **脱敏白名单的具体字段** —— 哪些字段允许上屏（§10 风险 1）
4. **简报可见窗口** —— 24h 是否合适？
5. **是否需要触摸回传** —— 建议 P6 之后再说（见 §10）

---

## 10. 剩余风险

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **敏感信息上屏**（最高优先级）—— 简报是 agent 生成的，可能带密钥/客户数据/私有路径 | 工具 description + skill 双重约束；服务端做正则兜底扫描（检测 `sk-`、`ghp_`、`AKIA` 等模式）并拒绝或打码 |
| 2 | **简报质量** —— agent 可能写废话或过度汇报，副屏沦为噪声源 | skill 的「何时不发」规则 + `supersedes` 去重 + 服务端长度硬截断 |
| 3 | 多终端刷屏 | 每 terminal 限速 + 板上策略 |
| 4 | DHCP IP 漂移 | DHCP 保留（先）/ `POST /register`（后） |
| 5 | 电量 | `next_poll_after` 自适应 |
| 6 | 明文 HTTP 无认证 | 仅绑 LAN；未来加固件 token |
| 7 | 触摸回传的安全边界 | 「点一下就能取消 agent 任务」风险不低 → 若做，用**单按钮语义**（长按=确认告警），不做任意命中测试 |

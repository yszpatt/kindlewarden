# kindlewarden — 版面规格

> 目标设备：Kindle Paperwhite 3，1072 × 1448 @ 300ppi，16 灰阶。
> 本文是渲染器（P0）的实现依据。
> 已锁定：板块 = `alerts` / `briefs` / `todos` / `ambient` / `statusbar`；
> 布局 = 垂直堆叠 + 权重；板上策略 = `all`（按时间倒序混排，不分组）。

---

## 1. 画布与安全区

```
        ← 1072 →
   ┌─────────────────┐  ▲
   │ 40px margin     │  │
   │  ┌───────────┐  │  │
   │  │  content  │  │ 1448
   │  │ 992 × 1368│  │  │
   │  └───────────┘  │  │
   │ 40px margin     │  │
   └─────────────────┘  ▼
```

| 项 | 值 |
|---|---|
| 画布 | 1072 × 1448，8-bit 灰度（PNG `L` 模式） |
| 外边距 | 40px（四边，避开边框遮挡） |
| 内容盒 | x ∈ [40, 1032]，y ∈ [40, 1408] → **992 × 1368** |
| 底色 | 白 `#FFFFFF` = 255 |
| 主文字 | 黑 `#000000` = 0 |
| 次级文字 | `#777777` = **119 = 17×7** |
| 弱文字 | `#999999` = **153 = 17×9** |
| 分隔线 | `#DDDDDD` = **221 = 17×13**，1px |

### 1.1 水平网格：只有两条基准线

「规整」几乎全部来自**竖向对齐**。整个画面只允许两条左边缘基准线：

| 常量 | 值 | 谁吸附在上面 |
|---|---|---|
| `GUTTER_X` | `MARGIN + 24` = 64 | 简报状态符号、待办勾选框（**图标列中心**） |
| `TEXT_X`   | `MARGIN + 58` = 98 | 简报标题、简报摘要、待办文字（**正文左边缘**） |

> ⚠️ 不要再用 `MARGIN + 22` / `MARGIN + 78` 这类就地魔数。
> 之前每类元素各算各的偏移，改一处就错位一处 —— 简报的文字列和待办的文字列
> 差了几个像素，单看每一行都"没问题"，整屏扫下来就是歪的。

唯一的例外是**告警条**：反白块里 52px 的三角图标会顶到 56px 的大标题上，
所以告警条内部自成一套（图标 `MARGIN + 54`、文字 `MARGIN + 104`）。
反白方块会放大任何对齐误差，这里的坐标必须显式写出来、不能复用正文网格。

> ⚠️ **灰阶必须对齐到设备网格。**
> PW3 是 16 灰阶，量化网格是 `255 / 15 = 17` 的倍数（0, 17, 34, … 255）。
> 把灰色选在网格上，文字就不会被抖动成噪点。
> 上表的三个灰值全部精确落在网格上 —— mockup 的 16 灰阶量化版与原始版
> 肉眼看不出差别，就是这么来的。
> **换任何颜色都要检查 `值 % 17 == 0`。**

> ⚠️ 外边距不是装饰：Kindle 边框可能遮挡最边缘几像素，FBInk CLI 手册明确
> 建议从第 1 列/行开始而非第 0 列/行。

## 2. 字号阶梯

300ppi 下，中文正文需要比拉丁字母更大的字号才在 1–3m 距离可读。

| 用途 | 字号 | 物理高度 | 每行中文字数 |
|---|---|---|---|
| 告警标题 | 64px | 5.4mm | ~15 |
| 简报标题 | 44px | 3.7mm | ~22 |
| 待办条目 | 40px | 3.4mm | ~24 |
| 时间（ambient） | 56px | 4.7mm | — |
| 简报摘要 / 次级信息 | 32px | 2.7mm | ~31 |
| 板块标题 | 30px | 2.5mm | — |
| 状态栏 | 26px | 2.2mm | — |

**字体**：服务端渲染，用思源黑体 / Noto Sans CJK SC（Regular + Bold）。
字体文件只存在于 host，**不需要也不应该传到 Kindle 上**（这正是服务端渲染的好处之一）。

**符号**：`✓ ◐ ✗ · ☐ ☑ ⚠` 这些字符不依赖系统字体 —— 在渲染时用**矢量绘制**
（线段/圆弧），不要用字体 glyph。中文字体常缺这些符号，且灰度量化后细笔画会糊。

## 3. 垂直分区

```
 y=40   ┌────────────────────────────────────────┐
        │  alerts        （0 或 196px）            │  条件区
 y=248  ├────────────────────────────────────────┤
        │                                        │
        │  briefs        （弹性，flex 2）          │  ← 核心
        │                                        │
 y=??   ├────────────────────────────────────────┤
        │  todos         （弹性，flex 1）          │
        │                                        │
 y=??   │  ┈┈┈┈ 内容区终止线（欠载时才画）┈┈┈┈     │
        │  ambient       （132px 固定）            │
 y=??   ├────────────────────────────────────────┤
        │  statusbar     （72px 固定）             │
 y=1408 └────────────────────────────────────────┘
```

**实现取值（已由 mockup 验证）：**

```
GAP          = 12     （分区之间的间距；比标题行内的呼吸更紧，
                       让"标题贴着内容"而不是"标题悬在两块之间"）
LABEL_H      = 62     （板块标题：字 34 + 线下 20 呼吸）
STATUS_H     = 72
AMBIENT_H    = 132
ALERT_H      = 196
BRIEF_ITEM_H = 128
TODO_ITEM_H  = 64
CONTENT_RULE_GAP   = 30   （终止线 → ambient）
MIN_RULE_CLEARANCE = 12   （终止线与末行内容的最小空隙，不够就不画）

status_y  = 1408 − 72               = 1336
ambient_y = 1336 − 12 − 132         = 1192
elastic_bottom = 1192 − 12          = 1180

无告警：elastic_top = 40            elastic_h = 1140
有告警：elastic_top = 40+196+12=248  elastic_h =  932

avail     = elastic_h − 2×62 − 12      （两个板块标题 + 中间间距）
briefs_h  = avail × 2/3
todos_h   = avail − briefs_h
```

| 场景 | elastic_h | briefs 区 | 可放 | todos 区 | 可放 |
|---|---|---|---|---|---|
| 无告警 | 1140 | 664px | **5 条** | 332px | **5 条** |
| 有告警 | 932 | 512px | **4 条** | 256px | **4 条** |

### 内容区终止线（`content_rule_y`，可为 `None`）

欠载时，内容与 ambient 之间画一条贯通细线，让留白读起来是「有意为之」
而不是「漏了东西」。两个已踩过的坑，规则就写在这里：

| 情况 | 行为 |
|---|---|
| 留白足够（≥ `MIN_RULE_CLEARANCE`） | 画在 `ambient_y − CONTENT_RULE_GAP` |
| 内容塞满弹性区，线会压到末行 | **不画**（`content_rule_y = None`） |
| 空态 / 无内容板块 | **不画** |

> ⚠️ 这条线曾经写成 `ambient_y − GAP + 8` —— 它**偷偷依赖 GAP 的值**。
> 把 GAP 从 24 调到 12 之后，线与 ambient 之间只剩 4px，贴到了一起。
> 现在间距用**独立常量**表达：`GAP` 管"分区之间"，
> `CONTENT_RULE_GAP` 管"终止线与 ambient"，两者语义不同，不该绑在一起。
>
> ⚠️ 也不能无条件画：`alert=True` 且内容满时，线会落到最后一条**之上**，
> 表现为一条删除线横穿末行的分隔位置（实测差 −4px）。
> 留白不存在时不画线，比画一条压住内容的线诚实。

### 分区标题行（`LABEL_H` = 62）

标题行不是"一行字"，是**一条把板块钉在内容上的横线**。层级靠三件事建立，
而不是靠把字放大：

| 元素 | 位置 | 样式 |
|---|---|---|
| 板块名 | 行顶 `+0` | 30px **粗体**、`GRAY`（比正文的黑弱一级） |
| 溢出计数 | 行顶 `+4`、右对齐 | 30px、`LGRAY` |
| 分隔线 | 行顶 `+42`，贯通内容宽 | 1px `RULE` |
| 线下呼吸 | `+42 → +62` | 20px 空白（正文从这里开始） |

> ⚠️ **线上呼吸 vs 线下呼吸是不对称的**：标题字上方只有 0px、
> 下方到正文有 20px。第一版是 `LABEL_H=52`（线下只有 10px），
> 渲染出来标题那条线与简报标题的笔画几乎贴在一起，像"标题压着内容"。
> 把线下呼吸加到 20px 之后，标题才真正读成**内容的上边界**。
>
> 加这 10px 会吃掉一整行内容，所以同步把 `GAP` 从 22 压到 12 ——
> 分区之间的空隙本来就该比标题行内的呼吸更紧。

> 板块名刻意用灰色而非黑色：正文（简报标题、待办）才是这一屏的主体。
> 标题抢成黑色会让每段内容都"从属于"标题，扫视时反而找不到起点。

### 溢出与欠载规则

- **条数是算出来的，不是配的**：`N = floor(区域高度 / 单条高度)`
- **溢出**：超出 N 条的，截断不显示，并在板块标题右端标 `还有 N 条`
  （e-ink 不能滚动，必须明说）
- **空板块整个省略**：内容为 0 的板块**不画标题**。
  留着标题会渲染出一大片「标题 + 空白」，看起来像渲染失败 ——
  和空态那个 bug 是同一类，只是发生在单个板块而不是整块板。
- **欠载时内容垂直居中**：弹性区里内容填不满时，余量**上下均分**。
- **底部锚点不变**：ambient 与 statusbar 永远贴底，不会因为内容少而浮上来。

> **关于「居中」这个决定的由来**：最初的规则是「余量一律作为尾部留白」，
> 理由是保持内容顶对齐的稳定性。但实测推一条简报上去，
> 结果是「一条简报顶在最上面 + 下面 950px 空白」——
> 看起来比居中摆放**更像加载失败**。居中之后同样的内容读起来就是「有意为之」。
>
> 锚点稳定针对的是**底部固定分区**；弹性内容随内容量浮动是正常的，
> 因为内容变化本身就意味着屏幕要重绘。

| 场景 | 表现 |
|---|---|
| 内容填满弹性区 | 居中退化为顶对齐（位移为 0） |
| 只有 1 条简报 | 该条居中显示，上下留白均分 |
| 待办为空 | 「待办」标题整块消失，空间回流给简报 |

## 4. 各板块设计

### 4.1 `alerts`（条件区，0 或 196px）

只在存在**未解决告警**时占位。一次最多显示 **1 条**（最高优先级），
更多则显示 `+N 更多`。

```
   ↓54        ↓104                              ↓1032
┌────────────────────────────────────────────┐
│  ⚠    需要你介入                             │  +26  30px 反白弱化
│       允许执行 rm -rf build                  │  +74  56px 粗体
│       session: refactor-auth · 等待 3 分钟    │  +146 30px 反白弱化
└────────────────────────────────────────────┘
```

- 视觉：黑底白字（反白），是**最强注意力信号**
- 反白面积 992 × 196 ≈ 全屏 13%，可接受
- 残影由 `-W GC16 -f` 的闪刷清除（刷新稀少，闪一下反而有帮助）
- 若嫌残影，退化为「左侧 16px 黑色竖条 + 正常黑字白底」

> ⚠️ **告警条内部自成一套对齐，不复用正文网格。**
> 反白方块会放大任何对齐误差，而且 52px 的三角图标若放在 `GUTTER_X`（64），
> 会顶到从 104 起的 56px 大标题上 —— 第一版实测就是这么重叠的。
> 所以图标固定在 `MARGIN + 54`，"需要你介入"这个小标签与标题同列（`MARGIN + 104`）。

### 4.2 `briefs`（核心，弹性）

单条高度 **128px**，内部水平线固定：

```
       ↓GUTTER_X   ↓TEXT_X                        ↓x=1032
┌────────────────────────────────────────────────────┐
│  ✓  修复了 auth 模块 token 刷新的竞态条件   14:32  │  +4   标题 44px 粗
│     backend · 把定时器刷新改为惰性刷新        │  +66  元信息 32px 灰
│ ──────────────────────────────────────────────── │  +120 1px RULE
└────────────────────────────────────────────────────┘
```

| 元素 | 规格 |
|---|---|
| 状态符号 | 矢量绘制，中心在 `GUTTER_X`，与**标题第一行**视觉居中（`y+34`） |
| 标题 | 44px Bold，从 `TEXT_X` 起，单行，超出用 `…` 截断 |
| 时间 | 30px 灰色，**右对齐**于 x=1032，与标题同基线（`y+16`） |
| 元信息 | `project · summary`，32px 灰色，`y+66` |
| 分隔 | 条目底部 `y+120`，1px `RULE`（随条目高走，不写死） |

> **时间戳与标题第一行对齐，不是与整条居中** —— 整条 128px 里有两行文字，
> 居中会让时间戳浮在两行之间的空档上，读起来像掉队了。
>
> **元信息用 ` · ` 连接而不是分列**：它是标题的注解，不是独立字段。
> 分列会额外引入一条竖线，与"全屏只有两条基准线"的原则冲突。

**溢出提示**：板块标题行右端显示 `还有 N 条`（灰字，与标题同行，不额外占高度）。
e-ink 不能滚动，所以**必须明说**还有多少条没显示，而不是假装没有。

> 除此之外，`briefs` 的标题 + 摘要合计宽度有限。
> mockup 暴露出的实测约束：一条简报的**摘要（含 project 前缀）单行约 28 个中文字**。
> 超出即被截断 —— 这已回写进 skill 硬性要求（见 `skills/kindle-brief/SKILL.md`）。

状态符号映射：

| status | 符号 | 附加 |
|---|---|---|
| `ok` | ✓ | — |
| `partial` | ◐ | 标题后缀 `（有遗留）` |
| `failed` | ✗ | 标题**加粗加重**，保留更久 |
| `info` | · | 整体降为灰色 |

**`project` 字段只作为标签显示**（策略 `all` 不分组），不做分组头。

### 4.3 `todos`（弹性）

单条高度 **64px**：

```
       ↓GUTTER_X   ↓TEXT_X              ↓x=1032
    ☐  补 auth 模块的删除用户测试用例
    ☑  更新 README 的部署说明              14:20
```

- 勾选框中心在 `GUTTER_X`、文字从 `TEXT_X` 起 —— **与简报同一条竖线**
- 40px；勾选框与文字都在 `y+8..y+56` 这条带子里垂直居中
- 已完成的降为 `LGRAY` 并加删除线
- 条间细线在 `y+58`，**最后一条不画** —— 否则板块尾部会多出一条悬空的线

> ⚠️ **数据源缺口（待定项，见 §8）** —— 这个板块的内容从哪来，尚未定义。

### 4.4 `ambient`（132px 固定）

```
      14:32            10月10日 周五            ☀ 24°C
      ↑ 56px           ↑ 32px                  ↑ 32px
```

- 时间居左（56px），日期居中（32px），天气居右（32px）
- **日期在内容区（992px）内居中，不是在画布上居中** ——
  画布居中会让它与右侧天气挤在一起
- **天气是可选子字段**：需要额外集成（API + 城市），缺失时该槽位留空
- 只有时间/日期也能独立工作 —— 这是让副屏在没任务时也不废的最低成本手段

### 4.5 `statusbar`（72px 固定）

```
   简报 4 条 · 待办 2 项        数据 3 分钟前 · 源正常
```

- 26px，整体灰色
- 左：计数
- 右：**数据年龄 + 源健康度**（诚实性的落地，见架构文档 §6.4）
- 顶部 `+6` 一条贯通细线，把它与 `ambient` 分成两段 ——
  之前两者只靠 22px 空白分开，灰阶上读起来像同一块内容的第二行

三态文案（必须能区分）：

| 情况 | 文案 |
|---|---|
| 正常 | `数据 3 分钟前 · 源正常` |
| host 不可达 | `数据 陈旧 42 分钟` |
| 网络断 | `连接中断 8 分钟`（Kindle 本地计时） |

## 5. 空态

**必须设计空态。** 否则无法区分「没事干」和「挂了」。

> ⚠️ mockup 第一版就是反面教材：常规布局 + 空列表渲染出来的效果是
> 「两个板块标题下面空空如也」，看起来像崩溃，而不是空闲。
> **空态必须是一个独立模式，不能靠常规布局「自然得到」。**

空态**不套用常规分区**（没有内容就没有锚点稳定的顾虑），
而是一个整体居中的独立画面：

```
┌────────────────────────────────────────────┐
│                                            │
│                  空闲                       │  120px Bold 灰
│           副屏已就绪，等待简报                │  38px 弱灰
│                                            │
│                 14:32                      │  150px Bold 黑
│           2026年10月10日 周五                │  38px 灰
│                                            │
│                                            │
│      通过 MCP 发布简报后，会显示在这里         │  28px 弱灰
├────────────────────────────────────────────┤
│  简报 0 条 · 待办 0 项      数据 1 分钟前 · 源正常 │
└────────────────────────────────────────────┘
```

要点：
- 大时钟占据视觉重心，让空屏显得**有意为之**
- 底部提示语顺带承担「怎么用」的引导
- `statusbar` 仍在原位，保持诚实性信息不断供
- 一旦有任何内容进来，就切回常规分区布局（布局跳变本身就是「有事发生」的信号）

## 6. 渲染管线

```
Brief/Todo/Alert 数据
      │
      ▼
  布局计算（纯函数）
  - 分区高度分配
  - 每条内容 → 槽位 (x, y, w, h)
  - 文本截断（按像素宽度，不是字符数）
      │
      ▼
  绘制（Pillow, mode="L"）
  - 文本：CJK 字体渲染，无需额外抗锯齿设置（8-bit 灰阶天然抗锯齿）
  - 符号：矢量绘制
  - 输出 1072×1448 PNG
      │
      ▼
  /screen.png  →  Kindle: fbink -g file=...,dither -W GC16 -f -q
```

**文本截断必须按像素宽度测量**（`font.getlength()`），不能按字符数 ——
中文全角、英文半角、数字宽度都不同。

## 7. 硬约束备忘

| 约束 | 后果 |
|---|---|
| **e-ink 不能滚动** | 只显示最近 N 条，老的自动消失；重要的靠 `pin` |
| **全屏重绘** | 分区锚点必须稳定，位置跳变会让人以为出事了 |
| **像素量化到 16 灰阶** | 细笔画符号会糊 → 符号用矢量画粗一点 |
| **不能滚动看历史** | 接受这个限制，不要试图绕过（不做翻页交互） |

## 8. 待定项

### 8.1 `todos` 的数据源（**缺口，需定义**）

这个板块的内容来源没定。两个候选来源语义**完全不同**，混淆会让人困惑：

| 来源 | 语义 | 生命周期 | 覆盖范围 |
|---|---|---|---|
| `warden_todo(...)` MCP 工具 | **副屏的待办板** —— 人/agent 主动往板上放的事 | 持久，直到勾掉 | 跨所有 harness |
| DSH `todo/write` 事件 | **当前任务的内部计划** —— agent 自己排的步骤 | 随会话结束失效 | 仅 DSH |

**建议：`todos` 板块只放前者**（副屏待办板，跨终端通用）。
后者的定位是「进行中任务的进度」，更适合放进 `briefs` 顶部的一行活动指示，
或者干脆不上屏（它属于主屏）。

需要确认：`todos` 是给**人**用的（我记下要做的事），还是给 **agent** 用的
（agent 告诉我下一步要做什么）？这决定 MCP 工具的语义和权限。
